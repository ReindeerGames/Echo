# WhatsApp operator assistant

The configured owner can message Echo directly for a read-only operational view. Echo authorizes the sender against the selected owner contact, reads only its structured MariaDB state, and audits the interpreted intent without storing the question body in the audit event.

Selecting an owner in the control plane atomically queues a private confirmation describing the notification scope and the `brief` command. If that message later remains pending or becomes dead, the same durable outbox state is visible on Overview and System; Echo never silently treats a half-saved owner change as complete.

Under **WhatsApp → Daily briefing**, the owner can opt into one automatic brief at an explicit local time and IANA timezone. Echo skips rendering while the schedule is disabled, before the local due time, or while no owner is configured. The outbox message, audit event, and last-sent local date commit atomically, so scheduler retries and restarts cannot send two briefs for the same local day. Immediate alerts are independent of this schedule.

When OpenAI is configured, requests outside the deterministic command set use the Responses API with `store: false`. Echo keeps a bounded local conversation history and gives the model only nineteen function tools: current status, open alerts, active/upcoming maintenance, service search, service detail, correlated service investigation, worker queue, privacy-safe WhatsApp delivery diagnostics, deployment records, project listing, estate coverage gaps, joined project health, bounded GitHub estate health, one live read-only GitHub repository status with five recent commit summaries, GitHub catalogue coverage, bounded repository text search, safe recent activity, recent incident search, and incident detail. Tool outputs, duration, success or failure, and the final reply are recorded locally for review under **Assistant**. There is no shell, SSH, general web, code execution, maintenance mutation, deployment mutation, retry, or other write tool.

Service detail includes observer freshness, evidence age, alert fingerprints and times, plus a strict allowlist of useful operational counters such as disk, memory, load, HTTP latency, HTTPS certificate expiry, backup/artifact age, container lifecycle, health, restarts, and heartbeat policy. Certificate subjects, issuers, SANs, backup paths, and filenames are not exposed. Arbitrary detail keys and free-form failure text are never sent to the model, so a custom observer cannot smuggle credentials or unrestricted logs through monitoring evidence. Evidence objects above 64 KiB are omitted. Tool collections are bounded and declare when results were truncated.

Supported requests include:

- `brief`, `daily brief`, or “good morning” for runtime health, monitoring coverage, open alerts and incidents, deployments needing attention, and bounded GitHub workflow health
- `status` or “how are things?” for the estate summary
- `coverage`, `setup status`, or “what isn't monitored?” for projects missing repository, group, service, heartbeat-policy, or fresh observer coverage
- `activity`, `audit`, or “what happened?” for recent action/outcome/resource/time audit fields without actors or metadata
- `alerts` or “anything wrong?” for open runtime conditions
- `maintenance` or “planned maintenance” for active and upcoming service windows
- `ack <code>` to acknowledge the exact open alert named by a private notification and pause its reminders
- `services` for the operations catalogue
- `service <name-or-key>` for a service's open alerts, latest observer evidence, and whether that evidence is fresh
- `investigate <service>` or “why is <service> failing?” to correlate up to 12 normalized signals, 10 target alerts, declared same-project dependencies followed by other attention-prioritized services, 10 project incidents, 10 deployments, and 8 configured repository workflow summaries
- `jobs` or “work queue” for queued, running, retrying, and dead worker jobs
- `deliveries`, `outbox`, or “why didn't WhatsApp send?” for channel type, attempts, retry timing, and safe WhatsApp failure categories
- `deployments` or “what is deployed?” for recent dispatch, rollback, and verification state
- `projects` for the project and repository map
- `project <name-or-key>` for one joined view of repositories, service freshness, open alerts, recent incidents, and deployments
- `github status` for current default-branch workflow health across up to 20 enabled repositories
- “which GitHub repositories are not configured?” for a read-only comparison of token-visible repositories and Echo's catalogue
- `repo <name>` for the configured default-branch head and up to ten recent GitHub Actions runs
- `incidents` for a bounded recent list with IDs, project, severity, status, and summary
- `incident <id>` for the report, latest diagnosis, bounded change/PR state, and deployment verification that followed
- `help` for the current command summary

Replies are capped for WhatsApp readability. The control plane remains the complete record.

When an accepted group mention contains a PNG, JPEG, or WEBP screenshot no larger than 5 MiB, Echo verifies the downloaded bytes, stores the image and SHA-256 hash with the incident, and supplies at most two screenshots to the configured vision-capable model at high detail. Image contents remain untrusted evidence and never authorize an action. The incident view exposes only attachment metadata, not a public media URL. Unsupported image formats, oversized or mismatched images, and failed downloads are omitted and recorded as categorized audit evidence. Retained attachment records and bytes are pruned after `ECHO_ATTACHMENT_RETENTION` (30 days by default). PDFs and other document types remain disabled until their separate processing path is configured safely.

To add evidence, reply in WhatsApp to the original report or any follow-up already retained for that open incident. Echo uses WhatsApp's quoted-message ID and the bound group—not fuzzy text matching—so a normal reply does not need another `@Echo` mention. The message and optional screenshot are appended idempotently, the group receives an acknowledgement, and Echo re-runs analysis over the bounded thread. Any pending approvals based on the older evidence revision expire automatically and must be requested again after the updated analysis. Resolved or closed incidents do not reopen through replies; mention Echo in a new message to create a new report.

Duplicate WhatsApp message IDs are idempotent and do not run tools or send another reply. Stateless Responses tool loops are capped at six rounds and eight calls. Echo preserves typed response items within the current loop, sanitizes tool errors before returning them to the model, and falls back to deterministic guidance when the Responses endpoint is unavailable.

Local owner messages and replies are retained for `ECHO_ASSISTANT_RETENTION` (30 days by default). `ECHO_ASSISTANT_HISTORY_LIMIT` controls how many recent messages, from 4 to 50, are supplied as conversational context. Successfully delivered outbox bodies use the independent `ECHO_WHATSAPP_OUTBOX_RETENTION` window (also 30 days by default). A supervised retention component prunes both at startup and daily, but never removes an unconfirmed or dead delivery.

Questions never authorize mutation. Approval commands remain deliberately narrow: `approve <code>` or `reject <code>` resolves only the pending immutable action bound to that one-time code. An unrecognized request cannot run a shell command, contact a production host, execute repository code, or infer permission to change infrastructure.

A service investigation correlates only evidence Echo has already collected through its bounded interfaces. Each section reports truncation, dependency, related-service, and repository checks are limited to the target service's project, individual GitHub failures do not expose raw errors, and monitoring details pass through the same strict allowlist as ordinary service questions. Declared dependencies and incoming consumers are identified explicitly and prioritized; other related services follow in attention order. All related services expose only catalogue identity, current state, open-alert count, and their latest normalized signal. Up to three recent default-branch commits per repository contribute only SHA, timestamp, and a redacted first-line summary; commit text and operator-entered dependency context remain untrusted evidence and are never treated as instructions. The result explicitly states that no logs, shell, SSH, source download, or mutation access was used. The model must distinguish timestamps and observed facts from a possible causal inference; a declared edge or temporal proximity alone is not proof that another service, deployment, or commit caused an outage.

When a service alert opens or reopens, its private owner notification includes ready-to-reply `service <name>` and `investigate <name>` prompts. Critical alerts also include an exact `ack <code>` command and repeat at the configured bounded interval until acknowledged or resolved. Only the configured owner can use the code; Echo resolves it deterministically against one currently open alert, outside the AI tool set. Acknowledgement pauses reminders but never monitoring or recovery. Reopening or escalation clears the previous acknowledgement. The first evidence prompt always uses deterministic retained evidence; the second uses the correlated AI tool when configured. Resolution notifications remain concise and do not invite unnecessary investigation.

GitHub inventory is a metadata-only comparison between repositories visible to the connected token and Echo's configured catalogue. It is capped at 100 returned entries, reports unlinked and configured-but-no-longer-visible counts, and never downloads source. Live source and status inspection remain restricted to repositories already enabled in Echo. A short name that matches more than one configured repository produces a clarification list instead of guessing. Status inspection reads only the configured default-branch head and recent Actions metadata and uses a 15-second deadline. For a natural question about application behavior, Echo may download the configured default branch into a private temporary directory for at most 45 seconds, scan at most 200 searchable text files and 8 MiB, and return at most 12 redacted excerpts with repository-relative line ranges. Credential files, key material, dependency trees, generated output, binary files, and files above 128 KiB are excluded. The temporary directory is removed after the request. Results declare truncation, are labelled untrusted evidence, and are never interpreted or executed as code.

The `status`, `alerts`, and `jobs` commands include persistent worker-heartbeat and stalled-queue state plus pending and dead WhatsApp delivery counts. `maintenance` reports active and upcoming per-service windows; alerts inside an active window remain visible and labelled even though their owner notifications are suppressed. Scheduling and cancellation are available only in the authenticated control plane, never as assistant tools. `deliveries` explains the active WhatsApp queue with direct/group channel type, state, attempt count, next-attempt or lease timing, and a normalized failure category. It never returns the body, destination JID, WhatsApp message ID, or raw gateway error, and it cannot replay a message. `status` and `alerts` also report Echo's supervised runtime components, including a missing, stopped, or retrying worker, watchdog, or enabled WhatsApp gateway. A component's first failure proactively sends one fixed, safe owner message; repeated restart failures are deduplicated, and 30 seconds of stable execution sends one recovery. If the gateway itself is unavailable, those lifecycle messages wait in the durable outbox. Only fixed component names and state labels are exposed; raw internal errors remain in server logs. A queue stall is reported only after ready work exceeds its configured grace period without a fresh worker heartbeat. Worker errors sent to the model are reduced to safe categories; raw job payloads and failure text are never included. The same state is visible on Overview and System, which remains useful when WhatsApp itself cannot deliver the warning. The deterministic commands remain available when AI is disabled or unavailable. Both paths preserve the separate exact-action approval boundary.
